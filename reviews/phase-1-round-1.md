# Phase 1 — Review round 1

## Verdict
Fail

The game, manifest loader and hot reload work, and the suite is green. But a mutation with an endless loop freezes the whole page, so the "a crashing module never takes down the game" promise does not hold. The sandbox frame also lets a module reach the network and replace other modules' code. The engine hard-codes Arena Survivor's API. There is 1 Blocker and 11 Majors.

How I verified: I reviewed commit `746863b` (the whole repository). Codex's dev server was still holding ports 5173/5174, so I ran the Playwright suite against it and ran the full `npm test` in a throwaway clone where the only change was the port numbers. I wrote probe mutations (E1–E8 below) only in that clone, never in this repository. I checked the running game by hand in a browser at http://127.0.0.1:5173.

## Exit criteria
- [x] `npm run dev` starts a playable game with a visible mutation list — the browser showed "Arena Survivor · LIVE" with Quick Feet, Gold Rush and Danger Zone all `active`. `snapshot().frame` kept advancing and the arrow keys moved the player (all smoke tests pass). One gameplay problem is filed separately as P1-R1-12.
- [x] Adding or removing a file changes the game within 2 s without a page reload — `adding and removing a mutation updates the list without navigation` passed (2.1 s, navigation count unchanged). Probe E6 also saw add and remove take effect in under a second.
- [ ] A deliberately broken mutation is disabled with a notice and the game keeps running — this holds only for a hook that throws synchronously (`a broken mutation disables itself…` passes). A hook that loops forever froze the whole page: two snapshot reads in a row timed out and the test page had to be killed (E1, **P1-R1-01**). A hook that throws asynchronously stays `active` and keeps throwing, with no notice (E2, P1-R1-05).
- [x] `npm test` runs the smoke test against each example and passes — in the clone: vitest 4/4, then Playwright 6/6, including `game plays for five seconds with 01-quick-feet.js / 02-gold-rush.js / 03-danger-zone.js`. In this repository, `npm test` crashed with `EADDRINUSE 127.0.0.1:5174` because the dev server was running (P1-R1-11). The same 6 Playwright tests passed against the running server. Playwright 1.64.1 needed `npx playwright install chromium` first; the README already says so.
- [x] The mutation API documentation is enough for an agent to write a module alone — I wrote all eight probe modules from `games/arena-survivor/docs/mutation-api.md` alone, and each loaded first time. Two behaviours are missing from it, though: when `onStart` re-runs, and that hooks must be synchronous (P1-R1-04, P1-R1-05).
- [x] `engine/` has no imports from `games/`, enforced by a test — `keeps the engine independent of games` passes, and `grep -rn "games/" engine` finds nothing. The test is narrow (P1-R1-20).
- [x] `--game games/arena-survivor` works; a missing or invalid manifest fails fast with a readable error — `--game games/nope` printed `Missing game manifest: …\games\nope\live-patch.json`. A bad manifest listed every issue, for example `entry: Invalid string…; reload.url: Must be a local WebSocket URL…; maxFileLines: Too big…`. Broken JSON printed `Invalid JSON in …`. All three exit before any port is bound.
- [x] Renaming the game folder and changing only the manifest path still works — in the clone, after renaming to `games/arena-renamed`, `--game games/arena-renamed` served `"entry":"/games/arena-renamed/src/main.ts"` and its mutations. However, `npm test` and a plain `npm run dev` both break after the rename (P1-R1-10).
- [x] `docs/adding-a-game.md` exists and matches the schema — every field in `engine/manifest/schema.ts` is described. The game-adapter contract in the same doc is incomplete (P1-R1-14).

## Findings

### Blockers
- **P1-R1-01** · `engine/mutation/frame.ts:25`, `engine/mutation/host.ts:46-49` — A hook that never returns freezes the whole game. Hooks run synchronously in a sandboxed iframe, and Chromium runs that iframe on the page's main thread. Probe E1 was a module whose `onTick` runs an endless loop after 1 s. The game stopped drawing, two `snapshot()` reads 2 s apart both timed out, and the test hit its 60 s timeout. There is no watchdog or deadline, and nothing disables the module. Probe E8 (a single 3 s busy-wait) caused a 3,033 ms frame gap in the host page, so long-but-finite stalls also hit the game directly. One bad loop on stream ends the run, and a module whose top-level code never finishes also stays `loading` forever. Suggested fix: run the module code off the main thread. One way is a dedicated Worker created inside the sandboxed frame, so it keeps the opaque origin and the CSP. Give every load and every event a deadline. If a reply is late, terminate the worker or remove the frame, and disable the module with a notice. Add a Playwright test with a looping module, and assert that the game keeps advancing and the module shows as disabled. Check that the approach also works in the browser that will actually show the game on stream (OBS's browser source, if that is the plan).

### Majors
- **P1-R1-02** · `engine/mutation/frame.ts:1-2`, `engine/mutation/host.ts:19-20` — A module can leave the sandbox's network block by navigating its own frame. Probe E3's `onStart` set `location.href` to an outside URL with `game.state` in the query string. The frame loaded that page, and the page ran `fetch` freely (no CSP applies after the navigation). It then posted 20 spawn actions to the parent. The host accepted them as the module's own actions (coins went from 4 to 24), because the frame keeps its `null` origin and its `contentWindow`. The comment on line 1 claims the CSP prevents navigation and workers. It prevents neither: CSP cannot block self-navigation, and blob workers are allowed through `script-src blob:`. This is the "reach network outside the `game` handle" case. Suggested fix: run the module where `location`, `parent` and the other frames do not exist (the Worker approach in P1-R1-01 does this). Have the host drop or disable a frame if it navigates (watch for its `load` event firing a second time). Correct the comment.
- **P1-R1-03** · `engine/mutation/frame.ts:6-10` — The frame's message listener accepts `load` and `event` messages from anyone, not just the parent. Probe E4 used two files, each of which passed the server gate (`error: null`). The attacker module looped over `parent.frames` and posted a `load` message whose source contained a forbidden token (`setInterval`, built by joining two strings). All four other frames, the three examples and the victim, swapped in that code and re-announced themselves as "Hijacked · active". Code that never went through `validateMutation` then ran under other viewers' names. A module can also post to itself to load arbitrary source, which makes the server-side token gate pointless. Suggested fix: inside the frame, accept a message only when its source is `parent`, and accept `load` only once. Better still, keep module code in a context that cannot see sibling frames at all (P1-R1-01). Add a test where one module tries to load code into another and the attempt fails.
- **P1-R1-04** · `engine/mutation/host.ts:36-42`, `engine/mutation/host.ts:56-59` — Any change to the mutation folder (or any module failing) unloads and reloads every module. That re-runs every `onStart` and wipes every module's internal state. In probe E6, a module spawned 10 enemies in `onStart`. Adding an unrelated empty module took enemies from 12 to 22, and removing it took them to 32. Danger Zone's `last` counter also resets, so it drops an extra bomb on every reload. On stream, each new patch, each rollback (Phase 3) and each crash will re-fire every earlier patch's start effects. That is the opposite of "nothing half-applied", and the mutation API doc does not mention it, so live-Codex cannot plan for it. Suggested fix: reconcile by file. Keep the frames whose source is unchanged, load only the added or changed ones, and remove only the deleted or failed ones. Then re-apply parameter changes without re-running other modules' `onStart`, for example by tracking each module's parameter writes and resetting only that module's writes when it goes. Document exactly when `onStart` runs. Add a test that adding or removing one module leaves the others' state and entity counts alone.
- **P1-R1-05** · `engine/mutation/frame.ts:25` — Async hooks are not covered by fault isolation. The frame calls the hook without awaiting it and sends the action list straight away. A hook that throws after an `await` (probe E2) is never disabled: it stayed `async · active`, the notice stayed empty, and it threw 62 uncaught errors in about 3 s. Its `game.spawn` after the `await` was silently dropped (enemies stayed at 2 → 2). Errors from timers are not caught either. The doc never says hooks must be synchronous, and Codex writes `async` often. Suggested fix: either reject promise-returning hooks with a clear error, or await them under the deadline from P1-R1-01. Also listen for the frame's `error` and `unhandledrejection` events and report them as module errors. State the sync-only rule (or the async semantics) in `mutation-api.md`.
- **P1-R1-06** · `tests/smoke.spec.ts:23-25` — The smoke test does not catch frame stalls, which the spec explicitly requires. The only check is that more than 100 frames ran overall. Probe E8 (`zz-stall.js`, one 3 s freeze at t = 1 s) passed `npm run smoke`: `ok 1 … game plays for five seconds with zz-stall.js (12.4s)`. Phase 3's dynamic gate relies on this test to reject runtime-breaking mutations. Suggested fix: record frame timestamps in the page during the 5 s run, and fail if any gap goes over a threshold (for example 250 ms) or the average frame rate drops well below the baseline without mutations. Add a test that a deliberately stalling module fails the smoke run.
- **P1-R1-07** · `engine/mutation/host.ts:26`, `games/arena-survivor/src/main.ts:20`, `games/arena-survivor/src/main.ts:86` — The 20-actions-per-event cap does not limit how many actions a module can trigger, because every spawn emits a new `spawn` event back to every module. Probe E5 was an "every coin splits in two" `onSpawn`. Frame rate fell from about 60 to 27 fps and coins went from 4 to 250. The 250-entity cap then deleted the oldest entities, so enemies dropped to 0. The game was quietly broken, and the smoke test would pass it, because nothing throws and frames still advance. The plan's own example "enemies split in two" invites exactly this module. Suggested fix: give each module an actions-per-second budget on the host side, disabling or throttling it with a notice when it overruns. Do not send a module the spawn events its own actions caused (or tag spawns by origin). When the entity cap is hit, refuse new spawns instead of deleting existing entities.
- **P1-R1-08** · `engine/game-api.ts:1-8`, `engine/mutation/frame.ts:19-24` — The engine owns Arena Survivor's API, so it is not game-agnostic. The following are all defined in `engine/`: the entity kinds (`enemy | coin | bomb`), the six parameter names, the snapshot shape (`player.lives`, `enemies`, `coins`), the event set and the four handle methods. `frame.ts` repeats the kind and parameter lists. A second game (a boat, a racer) cannot offer its own actions, parameters or events without editing `engine/`. That breaks the Phase 5 exit criterion "no `engine/` diff since Phase 4" and the platform pitch. Suggested fix: let each game declare its handle vocabulary: action names with argument schemas and limits, event types, and the hook names they map to. Do this through the manifest or a `describe()` on the game adapter. Build the frame's `game` handle from that declaration, and leave validation to the game, which already validates in `apply`. Keep only generic plumbing in `engine/`.
- **P1-R1-09** · `engine/game-api.ts:3-6`, `games/arena-survivor/docs/mutation-api.md:5-7` — The API is too narrow for free-form chat ideas, which is the first "Reviewer focus" question. A module cannot see or address individual entities: the state holds counts, not positions or IDs. It cannot move, remove, resize or re-colour an entity, cannot add a new kind, cannot draw text at a position, and gets no event for enemy-to-enemy contact or for an enemy being hit. Of the plan's six example ideas, only "gravity flips every 30 s" can be fully expressed. "Fire trail" is cosmetic only. "Enemies split when hit", "coins run away", "speech bubbles above enemies" and "touching enemies merge" cannot be built. Phase 3 needs at least 7 of 10 varied ideas to ship, and the module API is the main lever on that. Suggested fix: add a small, bounded entity layer. That means entity IDs and positions in `state` (capped), per-entity actions such as remove, move or set velocity, set radius and tag, a text-at-position action, and an `onEntityCollide` event. Write a one-line module sketch for each of the plan's six ideas in the API doc to prove they fit.
- **P1-R1-10** · `tests/smoke.spec.ts:5`, `tests/manifest.test.ts:10`, `tests/manifest.test.ts:27`, `vite.config.ts:9` — The test harness and the default dev start hard-code `games/arena-survivor`. In the clone, after renaming the folder: vitest failed 2 of 4 (`Missing game manifest: …\games\arena-survivor\live-patch.json`), Playwright reported `ENOENT … games\arena-survivor\mutations` and `No tests found`, and a plain `npm run dev` failed the same way. The manifest's `testCommand` (`npm run smoke -- --mutation {file}`) runs a root-level suite that ignores the manifest. So the Phase 3 runner cannot smoke-test any game except this one, and the plan's per-game `games/<game>/tests/smoke/` does not exist. Suggested fix: move the game's smoke test into the game folder. Have the smoke runner take the game folder (or read it from one config value) and find `mutationDir` through `loadGame`. Point the manifest's `testCommand` at it. Keep a single default game path in one place.
- **P1-R1-11** · `scripts/test.mjs:15`, `vite.config.ts:28`, `vite.config.ts:50`, `tests/smoke.spec.ts:34`, `tests/smoke.spec.ts:48`, `tests/smoke.spec.ts:66` — `npm test` and `npm run smoke` need exclusive use of fixed ports 5173/5174. They crash with a raw `Unhandled 'error' event … EADDRINUSE 127.0.0.1:5174` while `npm run dev` is running, which is exactly what happened in this repository today. In Phase 3, the runner must run the smoke command while the live game is up, so every dynamic gate would fail. The tests also write their fixture modules (`zz-broken-test.js` and others) into the real mutation folder, so pointing them at a live server would show them on stream. Suggested fix: let the smoke runner pick free ports, or take them from environment or flags, and pass them to both Vite and the reload relay rather than taking them from the manifest. Run smoke tests against a temporary copy of the mutation folder (or the runner's worktree), never the live one. Turn a port clash into a one-line readable error.
- **P1-R1-12** · `games/arena-survivor/src/main.ts:57-61`, `games/arena-survivor/src/main.ts:78`, `games/arena-survivor/src/main.ts:86` — The base game cannot last a stream-length run. Enemies spawn every 1.35 s and never leave. When lives hit 0, only lives, score and position reset; the swarm stays and keeps converging on the centre where the player respawns. In the running game, sampled at 63–70 s: `L3 → L2 → L1 → L3 …` every ~3 s with score 0, while enemies climbed 47 → 53. After the first minute, an idle or unlucky player is stuck in a "NEW RUN" death loop. Chat cannot fix it either, because no mutation can remove an enemy (P1-R1-09). The vision's "minute 1 vs minute 40" contrast needs a base game that survives 40 minutes. Suggested fix: clear or thin the arena on a new run. Add a natural limit or wave rhythm to enemy count (despawn, cap per kind, or waves with breathers). Reset `elapsed` per run or expose a separate run timer.

### Minors
- **P1-R1-13** · `engine/mutation/validate.ts:3`, `engine/mutation/validate.ts:9` — The token gate has false positives that will fail innocent ideas, and it misses the globals that matter. `"Coins become more important"` is rejected by `/\bimport\s*(?:\(|[\w*{])/`, and `"A medieval knight joins"` by the manifest's `eval` (plain substring match). Meanwhile `parent`, `self`, `top`, `frames`, `location` and `postMessage` all pass. Suggested fix: match tokens as identifiers outside string literals and comments (a tokenizer such as the one in `acorn` would do), and add the frame-escape globals to the engine list. Treat the gate as a guardrail; the runtime isolation in P1-R1-01 to 03 is the real boundary.
- **P1-R1-14** · `docs/adding-a-game.md:7`, `docs/architecture.md:5` — Both docs say `createGame` returns `apply`, `snapshot` and `destroy`. The host also calls `resetMutations()` on every sync, and `GameAdapter` requires `emit`. A second game built from the doc fails with a `TypeError` on the first sync and never loads a mutation. The doc also leaves out the reload URL rules (local host, explicit port, one path segment). Suggested fix: list every adapter method with its purpose, and add the URL rules.
- **P1-R1-15** · `engine/mutation/host.ts:22` — The host trusts the shape of a frame's messages. In probe E7, a module posted `{type:'ready'}` with no `meta`, which threw `Cannot read properties of undefined (reading 'title')` in the host page. The status had already been set to `active` before the throw, and the start event was never sent. Suggested fix: validate every incoming message against the expected shape, accept `ready` once per load, and disable the module on malformed input.
- **P1-R1-16** · `engine/client.ts:16-25` — The reload socket never reconnects; the page only says "Refresh to reconnect", and a refresh restarts the run. A file change between the `/api/mutations` fetch and the socket opening is missed until the next change. Suggested fix: reconnect with backoff, and on every (re)connect fetch `/api/mutations` again and sync.
- **P1-R1-17** · `engine/mutation/host.ts:39-41`, `engine/mutation/host.ts:72-77` — Rejected modules never appear in the patch list, and only the last notice is visible. After any other file changes, a failed module vanishes from the list too: it is skipped and no longer in `loaded`. A mod watching the stream loses track of what is broken. Suggested fix: keep rejected and failed modules in the list with their reason until their file changes or is removed.
- **P1-R1-18** · `engine/client.ts:7` — The engine's page hard-codes `ARENA SURVIVOR` and "Collect coins · Avoid enemies", which are game text inside the engine. Suggested fix: set the heading from the manifest `name` with `textContent`, and let the game (or the manifest) provide the hint.
- **P1-R1-19** · `engine/manifest/load.ts:14` — `examples` entries are never checked for escaping the game folder, because their pattern allows `../`. The Phase 3 prompt builder will read these paths into Codex's context. Suggested fix: run the same inside-the-folder and must-exist checks on every `examples` entry.
- **P1-R1-20** · `tests/manifest.test.ts:23` — The boundary test only matches `from '…games/…'` and `import('…games/…')`. It misses side-effect imports (`import '…games/…'`), template-literal dynamic imports and `require`, and it does not scan `vite.config.ts`, which holds the engine's dev server and relay. Suggested fix: resolve every import specifier in engine code and assert that none resolves under `games/`. Include the dev-server plugin, or move it into `engine/`.

### Nits
- **P1-R1-21** · `.tmp-renamed-game/` (empty, untracked, not ignored) and `vite.config.ts:10` (unreachable `if`) — remove the leftover folder, and drop or move the dead check.

## Working well — do not change
- The manifest loader: Zod schema, the escape and existence checks for `entry`, `mutationDir` and `apiDocs`, the 120-line ceiling a manifest cannot raise, and clear multi-issue error messages.
- `allow-scripts` without `allow-same-origin` and a `default-src 'none'; connect-src 'none'` CSP. Both hold for code that stays in the frame (storage and same-origin access are blocked); keep them as the outer layer.
- The host and game re-validate every action. Kinds, finite numbers, clamped parameters, hex colours and messages cut to 100 characters are all enforced on the game side, not just in the frame.
- No viewer or game text reaches HTML. The patch list and notices use `textContent`, messages draw on the Phaser canvas, and the only `innerHTML` is a static template.
- The server sends the full mutation list on each change, which makes deletions easy to reconcile. The navigation-count check in the hot-reload test is a good guard against accidental full reloads.
- The smoke test measures game time with `expect.poll` instead of assuming wall time, and checks finite state and an empty notice.
- Honest phase report: the known gaps (token gate is not proof of safety, fixed reload port) match what I found.
